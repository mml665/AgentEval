# AgentEval 产品需求文档（PRD）

**项目名称：** 面向异构 Agent 的自动化评测与回归分析平台  
**文档版本：** V1.1  
**目标产品版本：** MVP V1.0  
**项目状态：** MVP 迭代构建中，生产安全与真实裁判校准尚未完成验收；实际能力见 [构建状态](BUILD_STATUS.md)

**修订日期：** 2026-11-03  
**配套文档：** [系统详细设计文档](AgentEval_系统详细设计_V1.1.md)

## 1. 项目背景

大语言模型 Agent 的执行已从单轮问答发展到工具调用、多步骤工作流、检索增强生成和外部环境交互。最终答案正确并不代表执行过程可靠；最终答案错误也不能直接说明模型能力不足，问题可能来自工具、检索、执行环境或评分器。

当前常见问题包括：

1. 不同 Agent 项目重复建设测试脚本、评分器和报表，标准难以统一。
2. 缺少执行轨迹，无法将失败定位到具体步骤、工具参数或检索结果。
3. 模型、Prompt、工具及工作流更新后，缺少固定条件下的回归比较。
4. LLM-as-a-Judge 存在波动、格式错误和判断偏差，评分可靠性不足。
5. 基础设施失败、证据缺失与 Agent 失败混在同一指标中，结果可能误导决策。

AgentEval 通过统一接入、批量执行、证据采集、可配置评分和版本回归，提供可追溯的质量评估闭环。

## 2. 产品目标与原则

### 2.1 总体目标

以统一执行框架评测不同实现方式的 Agent，使开发者能够回答：本版本是否完成目标任务、失败发生在哪里、相较基线是否退化，以及现有证据能否支持发布决策。

### 2.2 MVP 核心目标

- 至少通过 HTTP 和 Python 两种接入方式跑通同一评测框架。
- 提供 LangGraph 示例适配，验证工作流步骤映射，不承诺兼容全部历史版本。
- 支持不可变 Benchmark 版本、版本化 Evaluation Profile 和执行配置快照。
- 支持批量执行、并发限制、超时、取消和可审计的故障恢复。
- 四种粒度各提供代表性能力：端到端、轨迹、工具调用、RAG 检索组件。
- 提供确定性规则与一种可配置 LLM Judge 接口。
- 展示指标、覆盖率、Bad Case、Trace 和可比版本的回归结果。

### 2.3 产品原则

1. **确定性优先：** 能用规则、结构化断言判断的任务优先使用确定性评分。
2. **证据约束：** 不根据最终答案推测不可观测的内部工具行为或检索指标。
3. **状态分离：** 执行是否完成、评分是否可用、任务是否通过、门禁是否通过分别表达。
4. **硬约束独立：** 安全违规与核心用例失败不能被综合高分抵消。
5. **可追溯优先：** 保存实际配置及证据；对无法完全复现的外部系统明确说明限制。
6. **恢复有边界：** 不因队列重投或等待超时自动重复执行有副作用的操作。

## 3. 目标用户与核心场景

| 用户 | 主要诉求 | 核心操作 |
|---|---|---|
| Agent 开发工程师 | 验证改动、发现新增失败 | 注册 Agent 版本、运行固定测试集、比较基线 |
| 评测工程师 | 维护测试集与评分标准 | 导入数据、发布 Profile、查看证据、导入复核标签 |
| 平台工程师 | 稳定执行与框架集成 | 部署可信插件、排查 Worker、维护凭据和访问策略 |

代表场景：

- **RAG + Tool Agent：** 检查最终答案、检索文档排序、工具选择与参数。
- **LangGraph 工作流：** 检查必要步骤、顺序约束、工具调用和任务结果。
- **版本回归：** 在相同数据集和评分协议下比较两个 Agent 配置版本，列出新增失败、修复及不确定变化。

## 4. 范围与边界

### 4.1 MVP 必须交付

| 模块 | MVP 范围 | 明确限制 |
|---|---|---|
| 项目组织 | 单租户、单可信团队，可建立逻辑 Project | Project 不构成租户安全隔离 |
| Agent | HTTP、可信 Python、LangGraph 示例 | 不接受上传并执行任意 Python 代码 |
| Benchmark | JSON/JSONL 导入、校验、标签、Golden Case、不可变版本 | 通过发布新版本修改数据，无在线协同编辑 |
| Profile | 版本发布、评分器配置、判定策略、执行参数和门禁 | 已发布版本不可修改 |
| 执行 | 批量、并发、重复试验、超时、取消、受限重试 | 不保证远端副作用可以撤销 |
| 评分 | 精确匹配、JSON Schema、工具、轨迹、RAG Recall/Hit/MRR/NDCG | 不承诺覆盖所有组件和业务正确性 |
| Judge | 一种结构化兼容接口，模型与 Rubric 可配置 | 外部凭据、网络及调用费用由部署方提供 |
| 分析 | Trace、评分证据、失败分类、指标覆盖率 | 缺少证据时不生成确定性归因 |
| 回归 | 严格比较、探索性比较、基础门禁 | MVP 不作显著性或因果结论 |
| 复核 | 人工标签 JSON/JSONL 导入和历史保留 | 无完整多人评分工作台 |
| Web | 配置、导入、创建与查询任务、结果及比较 | 不提供复杂可视化流程编排 |
| 部署 | API、Worker、PostgreSQL、Redis、前端的 Compose 配置 | 单机部署，不承诺生产高可用 |

### 4.2 后续版本

V2：项目级 RBAC、多用户评分工作台、CI 门禁集成、故障注入、受控环境重置、成本分析与统计增强。

V3：Coding/Browser Agent 沙箱、多 Agent 协作、多模态、大规模分布式执行。

### 4.3 非目标

不训练基础模型，不承担被测 Agent 的业务逻辑，不自动修复所有失败，不替代生产安全审计，不在 MVP 中提供通用代码沙箱或跨租户隔离。

## 5. 完整用户流程

1. 管理员配置可信插件、网络访问策略及密钥引用。
2. 用户创建 Project，注册 Agent，发布不可变 Agent 版本。
3. 导入 Benchmark；系统校验格式、用例身份和断言，展示问题并拒绝非法发布。
4. 发布 Profile，指定评分器、阈值、必需项、硬约束和执行参数。
5. 选择版本创建任务；系统先校验能力、输入、预算和重试资格。
6. 校验通过后冻结 Run Manifest，再调度执行。
7. 展示运行进度，区分 Agent 错误、基础设施错误和评分错误。
8. 查看结果及 Trace；评分失败可单独重评，原始记录保留。
9. 选择可比基线生成回归报告，查看变化及门禁证据。
10. 导出报告或导入人工复核标签，保留来源和审计记录。

## 6. 功能需求

### FR-01 Agent 与能力声明

- Agent 定义保存接入方式、负责人和描述；AgentVersion 保存不可变配置及代码/镜像标识。
- 能力至少包括工具 Trace、工作流步骤、检索结果、最终状态、Token 用量、取消、重置和幂等支持。
- 能力声明不等于实际证据。系统仍检查每次输出是否满足评分输入要求。
- HTTP 黑盒默认仅支持可观测输出；不能默认视为具备内部 Trace。
- Python/LangGraph 仅调用服务端预部署、列入允许清单的模块。
- 健康检查不触发业务调用，不被解释为所有任务均可成功执行。

### FR-02 Benchmark 与版本

- 支持 JSON/JSONL 导入，反馈行号、字段路径和校验原因。
- 用例支持输入、参考输出、预期工具、轨迹约束、检索相关性标签、状态断言、标签和环境配置。
- 发布时生成内容哈希、用例数量和版本记录；原始内容不可变。
- 同一 Benchmark 内 `case_key` 表示逻辑用例身份，版本内记录具有独立 ID。
- Golden Case 表示经标注的参考用例；是否为必须通过的核心用例由 Profile 另行指定。
- 不兼容的任务目标变化应创建新 `case_key`，避免误配历史用例。

### FR-03 Profile 与评分器

- 评分器声明实现版本、输入要求、配置 Schema、输出 Schema、粒度和质量维度。
- Profile 指定评分器配置、阈值、必需/可选、硬约束、执行参数及门禁。
- 可选评分器用于分析；必需评分器参与任务判定。权重仅生成辅助综合分。
- 禁止将评分异常、缺失证据或不适用自动转换为零分。
- 未发布或不存在的评分器版本不能创建可执行任务。

### FR-04 执行与恢复

- 支持项目和 Run 两层并发限制，记录排队、执行和评分耗时。
- 重复试验从创建时预先规划；失败重试是同一试验的后续尝试，分别编号。
- 默认不自动重试。仅在幂等保证或可验证环境重置满足策略时允许。
- Worker 异常退出后根据执行阶段恢复，禁止对未知副作用结果静默重跑。
- 提供取消请求及取消确认状态；无法确认远端停止时明确提示可能仍在运行。
- 超时以平台观测为准，记录实际终止是否已确认和迟到结果。
- Agent 执行已完成时，Judge 故障只重跑评分，不重调 Agent。

### FR-05 四种评测粒度

| 粒度 | 代表性评分 | 输入前提 |
|---|---|---|
| 端到端 | Exact Match、JSON Schema、声明式状态断言、Judge | 对应输出/状态/参考答案 |
| 轨迹 | 必要步骤、先后依赖、禁止行为、重复调用 | 已声明且完整的步骤或工具观测 |
| 工具 | 允许工具、参数 Schema、参数字段语义约束 | 可关联的工具调用和参数 |
| 组件 | Recall@K、Hit@K、MRR@K、NDCG@K | 排序后的文档 ID 与相关性标签 |

参数格式与语义分别评分；允许满足约束的替代轨迹，不强制与唯一参考路径一致。状态断言只能验证实际提供且来源明确的状态，不将 Agent 自述视为独立环境验证。

### FR-06 Trace、Bad Case 与复核

- 从 Run、逻辑试验、执行尝试定位到 Trace、工具调用及评分证据。
- 支持最终输出错误、工具选择、工具参数、轨迹、检索、安全、超时、评分异常等多个标签。
- 自动归因必须区分直接观测与推断；不能证明的原因标记待复核。
- 展示截断、脱敏、Trace 不完整等限制。
- 人工标签追加保存，包含目标结果、操作者、理由和时间；MVP 不覆盖原始评分或自动改变历史门禁。

### FR-07 回归与门禁

- 严格模式校验数据集、评分标准、执行约束及环境兼容性；允许声明的 Agent 配置变化作为比较对象。
- 探索模式展示不一致项，可比较原始指标，不输出发布通过结论。
- 新增失败和已修复按用例配对；存在未知结果时不得强制归为失败或修复。
- 重复试验展示每个用例的成功率和样本数，随机变化仅标记为疑似退化/改善。
- 门禁支持最低成功率、最大下降、P95 延迟、核心用例和硬约束。
- 门禁输出 `passed`、`failed`、`inconclusive`；必需证据不全不能判通过。

## 7. 统一指标与判定口径

### 7.1 四类状态

| 层次 | 含义 | 示例 |
|---|---|---|
| 执行状态 | Agent 调用的实际结局 | completed、agent_failed、timed_out、outcome_unknown |
| 评分状态 | 单项评分是否有效 | scored、not_applicable、missing_evidence、evaluator_error、pending_review |
| 任务判定 | 一次逻辑试验是否满足业务标准 | passed、failed、unknown、excluded |
| 门禁结果 | 当前证据能否满足发布标准 | passed、failed、inconclusive |

已证明的必需规则或硬约束失败优先判任务失败；没有失败但必需评分缺失时判 unknown。Agent 异常和执行超时计为任务失败；纯基础设施故障及取消不混入 Agent 成功率。副作用结局未知单列。

### 7.2 指标定义

- **任务成功率：** `passed / (passed + failed)`。分母为零时显示无可用值。
- **判定覆盖率：** `(passed + failed) / 预先规划逻辑试验数`。
- **未判定/排除数量：** 分别展示 unknown、infrastructure_failed、cancelled 等原因数量。
- **已确认成功占比：** `passed / 预先规划逻辑试验数`，作为覆盖率不足时的补充信息。
- **评分覆盖率：** 有效评分数 / 预期适用评分数；非适用项数量另列。
- **延迟：** Agent 调用端到端观测耗时，成功调用 P50/P95 与超时率、错误调用耗时分开展示。
- **Token/成本：** 仅统计来源可验证的已知用量，显示采集覆盖率；缺失不是零。Judge 用量单列。

重试不扩大逻辑试验分母；每次尝试仍单独保留，报告展示重试率和首尝试成功率，避免恢复策略掩盖原始质量。

门禁默认要求判定覆盖率 100%；项目可以显式调整阈值，但报告必须显示该配置。已证实的硬约束违规始终导致失败。

## 8. Web 页面与关键反馈

1. **项目概览：** 运行数量、状态、覆盖率、近期比较。
2. **Agent：** 定义、版本、能力、健康状态。
3. **Benchmark：** 导入预览、校验错误、版本和用例。
4. **Profile：** 评分器、适用条件、阈值、执行策略和发布校验。
5. **任务：** 创建、列表、进度、取消、异常恢复状态。
6. **结果：** 四类状态、指标分母、评分覆盖率、失败过滤。
7. **执行详情：** 输入输出、尝试记录、Trace、评分证据和原始异常。
8. **回归：** 可比性检查、变化清单、用例配对、门禁。

没有证据、没有数据和真实零值必须使用不同文案。取消、重试、超时都应显示对远端执行结果的确认程度。

## 9. 信任边界与安全要求

MVP 面向单可信团队。共享团队中的用户具备相同业务数据访问权限；管理员凭据与团队访问凭据分离，插件注册、密钥配置和网络策略变更仅管理员允许。逻辑 Project 不提供行级隔离，部署时必须明确提示此限制。

- API 默认鉴权，健康探针仅返回最小存活信息。
- 密钥以引用方式绑定配置；不通过读接口返回明文，不进入 Run Manifest。
- endpoint 访问按部署方允许清单控制，包括协议、主机/IP、端口与重定向策略。
- Trace、日志、导出文件实施脱敏；原始敏感制品同样受访问控制和保留策略约束。
- 输入、事件、上传文件、并发、运行时长和 Judge 预算有配置上限。
- 不接受不可信插件代码；被测输出和 Trace 对 Judge 属于不可信数据。

## 10. 非功能需求

以下为待验证的验收目标，不能写成已获得结果。

| 方面 | 要求 |
|---|---|
| 持久性 | 任务入队前持久化配置；结果与证据存在稳定关联 |
| 故障恢复 | 重复投递不生成重复有效结果；未知副作用不自动重执行 |
| 可观测性 | Run/Execution/Trace ID 贯通日志，区分业务与平台错误 |
| 容量 | 配置文件大小、事件数、制品大小和留存上限，达到上限明确失败或标记截断 |
| 性能 | 使用固定环境与模拟 Agent 验证并发上限，不对外部模型延迟作统一 SLA |
| 可维护性 | Adapter 与评分器通过统一接口扩展，有契约和版本测试 |
| 部署 | Compose 配置、迁移、初始化示例与健康检查可执行 |
| 可审计性 | 发布、取消、重试、重评、标签导入和配置变更有审计记录 |

## 11. 验收标准

| ID | 场景 | 验收条件 |
|---|---|---|
| AC-01 | 跨框架评测 | HTTP 与 Python 至少各完成一次真实执行链路；LangGraph 示例通过适配测试 |
| AC-02 | 四种粒度 | 每种至少一个评分器有正例、反例和缺失输入测试 |
| AC-03 | 数据冻结 | 发布后不可变；内容哈希稳定；非法导入返回定位信息 |
| AC-04 | 能力校验 | 不支持必需 Trace 的 Agent 创建任务被拒绝；运行时缺失证据标记 unknown |
| AC-05 | 超时与取消 | 区分等待超时和远端终止；迟到结果不覆盖已确定终态 |
| AC-06 | Worker 故障 | 覆盖调用前、调用中、调用后落库前退出；未知副作用不静默重跑 |
| AC-07 | 重复投递 | 同一逻辑执行不会产生两个有效结果，旧 Worker 写入受拒绝 |
| AC-08 | Judge 故障 | 格式错误、拒答、限流、超时均不直接计为 Agent 失败；评分可独立重跑 |
| AC-09 | 指标口径 | 超时计失败；基础设施故障单列；重复试验与重试分母正确 |
| AC-10 | 回归校验 | 不同 Benchmark/Profile 的探索性比较不能产生通过门禁 |
| AC-11 | 证据追踪 | 从失败定位到执行尝试、评分器版本、配置与实际证据 |
| AC-12 | 安全边界 | 未授权访问受拒；密钥不出现在 API、日志和导出快照；网络策略生效 |
| AC-13 | 部署 | 在文档指定环境中从空数据库启动并完成示例闭环 |

Judge 还需准备人工标注校准集，报告样本数、一致率、分歧类型、重复评分波动及无效响应比例；在缺少业务样本之前不承诺通用准确率。

## 12. 实施阶段与退出条件

| 阶段 | 主要成果 | 退出条件 |
|---|---|---|
| M0 契约冻结 | 指标、状态机、Schema、信任边界 | AC 的口径明确，核心歧义关闭 |

## 14. 风险与依赖

- 外部 Agent、模型 API 和环境变化可能限制复现；需记录版本可获得程度。
- 无内部观测的黑盒 Agent 不能完成全部粒度评测；需提前确认能力。
- 长耗时调用、并发与 Judge 请求产生费用；需配置预算和资源上限。
- 真实业务标准需要项目方提供标注与规则，平台不提供通用正确性定义。
- Python 插件依赖可信部署；未来开放上传需另行设计沙箱及权限体系。

## 17. 0.6 产品定位与用户闭环

产品定位调整为“面向 Agent 开发团队的自动化质量评测与回归决策平台”，核心决策是新版本是否更好、哪里退化、证据是什么、是否具备发布条件。

主用户为持续迭代 Agent 的开发者和质量负责人。主流程为质量工作台发现变化 → 三步向导建立有效评测 → 跟踪 Bad Case → 人工确认根因与修复 → 兼容复测 → 沉淀不可变回归集 → 生成三态发布建议。资源管理、组件与运行健康保留为支持能力。

本轮已实现质量工作台、三步向导、缺陷生命周期和固定发布评估。工作台指标来自同一候选批次；空值和证据不足不显示为通过。接入校验不虚称已经验证业务执行或内部能力。Bad Case 的确定性事实与候选解释分开，不能直接人工关闭未通过兼容复测的问题。发布建议为可发布、阻断、证据不足，绑定固定版本与批次，不直接执行部署。

新增验收：AC-18 向导预检失败不留下半成品资源，相同请求重复提交幂等；AC-19 问题保留事实、来源、处理和复测历史，改断言不得认定修复；AC-20 复测通过后加入长期回归版本且原用例不变；AC-21 开放阻断、证据不全或更新评分批次不生成可发布结论；AC-22 发布报告保存后不被后续重评或问题更新改写。

首次完成时间、接入成功率、证据可定位率、核心复测成功率等目标需真实用户试用建立基线，自动化测试不替代该验证。不承诺建议路线图中的周数为已确认工期。详细交互、口径和验收边界见 [0.6 产品验收](V0.6_PRODUCT_ACCEPTANCE.md)。
