# 0.12：当前发布包的部署与恢复验收

日期：2026-11-05。对应 AE-004 的运维部分，以及 AE-003 备份边界说明。保留 0010 数据结构、0.11 功能、历史快照和实际操作者；未增加评分器或框架。

## 1. 交付内容与范围

新增 `scripts/deployment_acceptance.py`，从已提交的 HEAD 生成 Git 归档，记录 commit 和源码摘要，在临时构建目录构建同一 Dockerfile。镜像包含完整前端和 Python 服务，新增 OCI revision 标签。构建工作树必须先提交；暂存目录不含工作区 `.env`、本机 data、未跟踪文件或 Git 凭据。

工具只接受新的 `*-acceptance` 项目，主栈及恢复栈分别拥有 API、Worker、Dispatcher、PostgreSQL 16、Redis 7 和独立卷。检测到同名容器或卷立即拒绝，不接管已有环境。API 随机绑定 loopback 端口；不会修改本机 8010 预览。固定故障步骤需要手动控制恢复，因此仅验收 override 的 restart 改为 no，正式 Compose 的策略不变。

所有 API Token、数据库密码、签名/指纹密钥和测试账户密码随机生成；清除继承的 AGENTEVAL_/POSTGRES_/COMPOSE_ 配置，并明确使用空 `--env-file`。临时账户只创建在本轮新库，密码不输出、不写报告。测试会从 legacy 切换至 team，并验证旧 Token 被拒绝；loopback Cookie 为本机演练配置，正式内网个人登录仍须按 0.9 HTTPS 方案部署。

## 2. 演练步骤与通过条件

| 步骤 | 实际动作 | 判定 |
|---|---|---|
| 固定包启动 | 构建前后端镜像，启动五服务，再执行一次 init-db | 前端可访问、/ready 成功、迁移可重复 |
| 排队恢复 | 停消费者，创建 LangGraph 任务，重启 DB/Redis/API，再启动消费者 | 同一 Run 保留排队后完成，结果正确 |
| 在途崩溃 | 等执行开始且 Trace 已落盘，对 Worker 容器 SIGKILL，等待过期租约后恢复 | 保留 1 次 Attempt、unknown 和已采集 Trace，占用仍 blocked，不静默重执或放行 |
| 依赖中断 | 在服务运行时分别停止 Redis、DB 并恢复 | /health 保持存活，/ready 降为 503，恢复后重新就绪 |
| 产品证据 | 实际执行退款反例、确认 Issue、修复复测、沉淀回归及发布三态 | 严重状态失败被阻断、复测关闭有兼容证据、固定快照可读取 |
| 团队配置 | 切 team、初始化临时管理员和项目只读成员、保存私人草稿 | 旧 Token 拒绝、跨项目 404、只读写 403、草稿按人隔离 |
| 一致备份 | 停 API/Worker/Dispatcher，确认无新增业务，再 pg_dump -Fc 和复制环境卷 | 记录全表数量/哈希、迁移版本、数据库包和所有环境文件 SHA-256 |
| 隔离恢复 | 校验备份文件后，新项目空库 pg_restore --exit-on-error，重复迁移，恢复环境卷和文件权限 | 启动应用前全表摘要完全一致、环境文件摘要一致 |
| 恢复后核对 | 核对实际镜像 ID，重新登录、查看报告并在原固定配置上执行新评测 | 固定发布 snapshot 未变，导出、角色/草稿边界、Worker 和环境卷写入可用 |
| 兼容回滚 | 构建明确旧 Git 提交，只切恢复栈镜像，不降级数据库 | 旧包迁移头与数据库一致，实际镜像已切换；旧包可重新登录、读取报告并完成新评测 |

PostgreSQL 的 Compose 健康检查使用 loopback TCP，避免把初始化阶段只监听本地 Unix socket 的临时实例视为可用。数据库重启和恢复前均等待依赖健康；备份前核对没有未结任务、评分批次或工作项，故障留下的 blocked/unknown 保持原样。

这里的退款/订单均为明确的集成夹具：真实运行 Python 和 LangGraph 代码及独立 SQLite 状态验证，但不等于两个真实业务 Agent 验收。Judge 不在这轮正式门禁中，未生成虚构的一致性或稳定性指标。

## 3. 运行方式与 CI

需要 Docker/Compose、Git 和 requirements.lock 中的 Python 依赖。在已提交且干净的工作区运行：

```powershell
.venv/Scripts/python.exe scripts/deployment_acceptance.py --project ae-local-012-acceptance --rollback-ref 61a71dab8ca82ca5ad328f9fca0146f2152fb12e
```

Linux 使用相同命令，Python 可替换为 `python`。`--port` 可选，默认随机选择空闲 loopback 端口。回滚参数是明确兼容的旧提交；缺省时 report.rollback 为 not_run，不能称已完成回滚验收。当前 0.11/0.12 都是 0010，无数据库 downgrade；跨结构版本必须另定迁移、恢复和应用兼容方案。

独立 `.github/workflows/deployment-acceptance.yml` 通过 workflow_dispatch 运行，参数 rollback_ref 指定旧提交；不是每次 push 自动运行的故障测试。普通 CI 保持 Python、浏览器及 PostgreSQL 集成检查。新边界测试覆盖非法项目名、继承秘密、归档逃逸/链接、已有容器或卷拒绝、失败停止范围、备份独占创建和环境内容校验。

## 4. 证据、备份与清理

结果写入 `.build/<项目>-<时间>/report.json`，记录源码/镜像/版本、schema、项目名、各步骤耗时、固定产品资源、数据库各表数量与摘要、备份和环境文件摘要、回滚目标、最终状态。失败也保存报告并停止已拥有的栈；不会执行 down -v、prune、删除备份或删除原数据卷。若停止失败，报告明确标记 containers_stopped=false，需要操作者按报告项目名核查。

同目录 `database.dump`、`environments/`、`restored-environments/` 是完整测试备份。整库备份与项目归档不同：前者包含身份、会话、个人草稿，必须保护；后者仍按 0.11 排除身份/私人草稿。Unix 新建 dump/report 使用 0600；Windows 的实际访问权限由目录 ACL 决定，工具不宣称已加密或已替部署方配置 ACL。不要把此目录直接复制到公开工件或版本库。

CI 仅上传 `report.json`，不上传数据库包、环境文件或含配置的 override。测试容器和卷由隔离 runner 生命周期承载；本机执行结束保留卷。报告不包含随机凭据，CLI 完成后不提供复用这些临时账户的管理入口。若需正式长期验收环境，应由部署方按团队初始化流程配置，而非接管测试栈。

源码暂存目录为临时目录，结束自动释放；原始工作区和服务不参与故障动作。容器卷和本机备份留存由操作者后续按明确项目名处理，本工具不执行销毁。

## 6. 部署方回滚顺序

1. 升级前记录当前/前一版镜像的固定 ID、迁移头及部署配置版本，备份 PostgreSQL、环境卷和部署秘密。切流前在隔离环境检查备份能恢复，记录固定 Run、评分批次和发布报告 ID。
2. 如果需回滚，先暂停入口，停止 API、Worker 和 Dispatcher，确认无未结工作或按运维流程保留未知状态。已持久化的执行和报告仍按原身份查询。
3. **仅在迁移头与结构兼容时**在 Compose override 中把 `api`、`worker`、`dispatcher` 都指向已经拉取或构建的上一版固定镜像，以 `docker compose -p <部署项目> -f docker-compose.yml -f <回滚覆盖文件> up -d --no-build api worker dispatcher` 同步切换应用。保留原 DB/环境卷，检查 `/ready`、团队登录、固定报告和一次试运行后再恢复入口。本轮 0010 上的 0.12→0.11 属于此路径。
4. 结构不兼容时，在新隔离库和卷恢复**升级前**备份，配对原镜像和密钥配置后核对证据，再按业务变更流程切流。升级后新增数据需另行评估迁移，不能从旧备份推断零数据损失。不得直接将旧 Worker 接到升级后的未知结构，也不靠自动 SQL downgrade 替代恢复。
