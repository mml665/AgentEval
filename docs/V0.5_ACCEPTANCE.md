# AgentEval 0.5：评测深度与可信度

本轮按代码审查建议改造现有模块化单体；不引入微服务或新的沙箱体系。以下实现可运行，真实业务通用性与真实模型校准仍需项目样本验证。

## 1. 独立环境状态验证

- Profile 可配置 `environment: {"adapter_id":"sqlite.refund.v1"}`，并增加 `state_assertion` 评分器。
- EnvironmentAdapter 的 prepare / observe / reset 在执行器内调用，Agent 只获得自己的环境上下文。每个 Execution 使用独立 SQLite namespace。
- 用例增加 `assertions.state.checks: [{"path":"/refunds","expected":[{"order_id":"1001","status":"requested"}]}]`。路径使用 JSON Pointer。
- 观察者直接读业务表，在重置前保存状态、时间、哈希和来源到独立 Execution 字段。Agent 返回的同名字段或 final_state 不能替代该证据。
- 正常返回后清空并核验环境；不确定副作用时保留隔离环境、不重置、不自动重试。已存在的 namespace 不被重新 prepare 擦除；管理员处置与留存清理仍需人工核验。
- 重评复用冻结快照，不读取已重置的现场。无状态探针的报告明确显示“仅验证输出与声明的过程观测”。
- 当前具体适配器是本地退款集成样例，不是任意生产数据库的通用写入或重置工具。HTTP Agent 如访问该样例，需要显式共享测试环境；不宣称跨主机路径可直接使用。

验收反例：`example.refund.liar` 返回完全正确的最终消息却不写表，exact_match 通过，state_assertion 失败。独立实现的 `example.refund.python` 和实际 LangGraph `example.refund.graph` 完成写表后通过。

## 2. 轨迹规则

用例 `assertions.trajectory` 保留 required_steps / dependencies，新增：

```json
{
  "required_steps": ["lookup", "respond"],
  "dependencies": [["lookup", "respond"]],
  "forbidden_steps": ["delete"],
  "forbidden_tools": ["delete_order"],
  "max_step_repetitions": {"lookup": 2},
  "max_identical_tool_calls": 2,
  "allowed_paths": [["lookup", "respond"], ["lookup", "fallback", "respond"]],
  "branches": [{"path":"/output/from_cache","equals":true,"required_steps":["lookup"]}],
  "recovery": [{"tool":"get_order","step":"fallback"}],
  "allowed_transitions": [["ready","done"], ["ready","failed"]]
}
```

这些约束均为可选，按任务需要组合。条件分支读取声明的观测或输出，不将其冒充独立状态探针。状态转换读取 `observations.state_transitions: [{"from":"ready","to":"done"}]`；完整通道须列入 observations_complete。异常恢复需要失败工具 end_ns 与成功 workflow Span 的 start_ns，证明恢复发生在失败之后；仅有步骤名称不足以证明时序。

已观察到的禁止行为或超限重复可在部分观测下证明失败；缺失必需步骤在不完整观测下是证据不足。重复工具参数缺失时不推断为相同调用。未配置循环规则时 loop_rate 不可用，避免显示虚假的 0%。dependencies 延续“首次出现顺序”的既有语义；复杂重复路径应使用显式 allowed_paths。该规则引擎不自动判断任意规划语义是否最优。

## 3. 工具证据与 ID 映射

工具评分显式接收 complete。声明通道完整但 Trace 为 partial / invalid 时，不用缺失调用证明失败。已匹配调用的确定错误仍可判失败；未提供名称、状态或输出等证据保持 missing_evidence。

- 默认 `match_by: "call_id"`，禁止隐式按工具名称合并。
- 可配置 `call_id_map: {"benchmark.lookup":"provider-call-42"}`，方向是期望 ID 到观测 ID，必须一一映射。
- 可显式选择 `match_by: "name_occurrence"`：同名工具第 n 个期望断言匹配观测数组中第 n 次调用。仅适用于完整且顺序可靠的工具通道，不与 call_id_map 混用；并行调用无法保证稳定顺序时应提供 ID 映射。
- 输出使用规则仍是声明式字段一致性验证，不宣称解决任意开放语义推理。

## 4. 评分器元数据、指标和门禁

GET `/api/v1/evaluators` 提供 granularity、quality_dimension、scoring_method、required_capabilities、required_evidence。每个新评分结果附带同样元数据。

LLM Judge 默认 E2E，也可配置 trajectory / tool / component，必须显式选择相应 actual_path；可用 expected_path 指向对应参考。运行前校验能力，观测不完整时不浪费模型调用预算。

报告按评分项提供平均得分、通过率、覆盖率与样本量；展示状态成功率、工具错误率、规则循环/恢复率、超时率、重复试验全成功率、Agent Token 覆盖率与 Judge 复核/错误率。专项指标以 canonical Execution 为准，重试不重复进入其分母，历史硬约束仍保留。不把不同量纲的四种粒度平均成综合质量分。

门禁增加 min_scoring_coverage、max_p95_latency_ms / min_latency_samples、max_tool_error_rate / min_tool_samples。性能或工具证据不足返回 inconclusive。原有安全硬约束零违规保持生效。无可信价格与完整 usage 时 Cost/Success 保持不可用；不实现虚假的金额门禁。Token 采集仅覆盖报告了 total_tokens 的 Agent，不与 Judge 请求消耗混算。

## 5. Judge 校准

- `benchmarks/judge_calibration.json` 是 8 条开发者编写的种子标签，含正确、改写、错误、部分正确、证据不足、否定及提示注入反例，待独立人工复核；不宣称已完成业务人工标注。
- POST `/api/v1/evaluations/{id}/calibration` 接收固定批次、Judge instance、标注来源及 case_key / label / rationale，输出一致率、混淆矩阵、覆盖率、错误/复核率、逐用例重复判定与得分波动。
- 错误及缺失预测保留在计划评分分母中；校准不改变历史裁判结果，也不冒充完整人工复核工作流。
- 前端含标签校准面板；`scripts/calibrate_judge.py` 通过普通 Run/Judge 协议执行重复评分并导出 JSON；也支持离线导入预测验证分析。模型密钥只从环境读取，无配置时明确拒绝，不回退模拟模型。

```powershell
.venv/Scripts/python.exe scripts/calibrate_judge.py --output .build/judge-calibration.json --repetitions 3
```

本轮未配置并调用实际模型，协议测试和分析器测试不能替代真实校准。提示注入样本仅用于测量防御表现，不保证注入免疫；不同 Agent 偏差、业务样本代表性需进一步实验。

## 6. 独立 RAG 接入

`sqlite.fts5` 使用真实 SQLite FTS5 / BM25 检索；`tfidf.cosine` 对给定候选进行独立 TF-IDF 余弦重排，替换之前两个示例共用同一函数的问题。返回有序文档 ID、有限分数及方法元数据。

`examples/rag_service.py` 可以作为单独 HTTP 进程运行。部署配置 AGENTEVAL_RETRIEVER_ENDPOINT / AGENTEVAL_RERANKER_ENDPOINT，并加入精确 HTTP_ALLOWLIST 后，注册 http.retriever / http.reranker；无需修改 Runner 或评分器。响应大小、ID 唯一性、有限分数及重排候选范围受校验。仅支持无内联凭据的测试服务，生产密钥提供器仍待后续。

`benchmarks/rag_relevance.json` 提供固定种子相关性标签，包括无关键词命中的反例。独立进程 smoke 同时测 Recall@2、MRR@2、NDCG@2，保留低于 1 的真实分项得分。它验证实际本地检索算法和 HTTP 接入，不等同于完成用户生产 RAG 的效果验收。
