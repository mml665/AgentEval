# AgentEval 0.7 评测范围与异常治理

日期：2026-11-04。此版本收敛质量工作台、Bad Case 和发布建议的范围，延续原执行和评分核心。

## 统一评测范围

工作台提供 Agent 身份、候选版本、基线版本、Benchmark 固定版本四个选择器。默认从最近已结束的评测建立候选范围，并选择同 Agent、同 Benchmark 固定版本的其他已测版本作为基线；用户可改选或取消基线。

质量指标来自该范围的固定比较候选批次；未建立比较时，来自所选候选版本和 Benchmark 的最近完成批次。无基线、无匹配比较或无匹配发布记录时显示空状态，不回退到另一个 Agent 的最新结论。切换范围时清理列表并拒绝迟到响应覆盖新范围。Bad Case 和发布列表沿用同一选择。

“项目总览”单独展示全项目的待确认、正式开放、已关闭和忽略数量。这些是历史记录数量，可能包含不同版本和重复 Trial，不是唯一业务缺陷数，也不是当前候选版本的阻断数量。负责人字段仍为可信团队手工记录，不代表身份认证或消息通知。

## 异常与正式 Issue

- 项目默认 `automatic`：评分终结事务写入 TrialAssessment、批次完成状态和待确认异常。执行器或评分器失败、证据不足也属于异常，不直接断言开发缺陷。
- `manual`：后续完成的评分不自动生成记录；保留批次导入、评测详情导入入口。导入同样产生待确认异常。
- 模式持久化，切换只影响后续评分完成，不删除既有记录，不回填以前未导入的失败。
- `kind=anomaly,status=open` 表示待确认；人工确认后 `kind=issue,status=confirmed`，再进入修复、待复测、复测关闭流程。正式 Issue 重新开放仍是正式 Issue。
- 批量确认和忽略仅适用于待确认异常；批量分配不隐含确认。忽略不屏蔽未来评分的新异常，同批次重新导入不复活忽略记录。
- 合并仅允许相同 Agent、Benchmark 和用例内容的活动记录。目标继承显式适用版本并集；任一来源为正式 Issue，目标保留正式类型；任一来源阻断级，目标保留阻断级。来源标记 merged 并关联目标，原始证据和事件不删除。
- 批量请求最多 100 条，携带每条 expected_revision，在 Project 锁下原子校验、提交；任一修订过期或范围不合法则整批回滚。

## IssueScope 与门禁

每个记录关联唯一 IssueScope：`agent_id`、`benchmark_id`、`case_hash`、`version_ids`。case_hash 为规范化输入与断言的内容摘要；同名用例但输入/预期变更不是同一身份。不同 Benchmark 即便内容相同也不继承问题。

版本范围采用不可变 AgentVersion ID 白名单，默认只有来源版本；不对任意版本标签做大小排序，不推断后续版本自动受影响。详情页可显式勾选同 Agent 的适用版本并提交理由和修订号，形成范围变更事件。已关闭、忽略或合并记录不直接修改范围。

发布时只纳入同时满足以下条件的 Issue：同项目、同 Agent、同 Benchmark、用例内容存在于候选 Benchmark 固定版本、候选版本 ID 在适用集合中、正式 Issue、阻断级、状态不属于 resolved/ignored/merged。记录来自历史批次不意味着自动阻断新版本。未确认异常不作为正式 Issue 阻断，但候选批次确定的硬约束失败、核心用例失败和证据不足仍按原门禁处理。

发布版本比较要求同 Agent 身份及同一 Benchmark 固定版本；跨 Agent、跨 Benchmark 的技术比较保留，但发布建议为 insufficient，附范围不匹配原因。兼容复测同样要求同 Agent 和同 Benchmark 身份、相同输入/断言、兼容策略，并且全部对应 Trial 通过。

发布快照冻结 evaluation_scope 与每个阻断项的 IssueScope 和 revision。后续范围修改、确认、合并或关闭不改写已保存的报告；旧版本发布快照保留其生成时策略，不追溯重算。

## API

沿用 `/api/v1` 鉴权前缀。

| 接口 | 行为 |
|---|---|
| GET `quality/workbench/{project_id}` | 返回 evaluation_scope、同范围固定指标、异常/正式问题数量、优先队列及匹配决策 |
| GET `quality/project-overview/{project_id}` | 显式全项目历史汇总，无发布结论 |
| GET/POST `quality/policy/{project_id}` | 读取/设置 ingestion_mode=automatic/manual |
| POST `quality/issues/bulk` | action=confirm/ignore/assign/merge，issue_ids、expected_revisions、note；merge 指定所选 target_issue_id |
| POST `quality/issues/{id}/scope` | expected_revision、version_ids、note；校验同 Agent |
| GET `quality/issues` / `quality/comparisons` / `release-decisions` | 可携带统一范围参数过滤；未携带范围的旧管理查询保留项目级语义 |

统一范围参数：`agent_id`、`candidate_version_id`、`benchmark_version_id` 必须同时提供，`baseline_version_id` 可选；版本/资源归属错误返回 422，未知 ID 返回 404。浏览器无有效范围时不请求项目级 Issue/决策列表。更新修订冲突返回 409。

## 迁移与验证

停止旧 API、Worker、Dispatcher 并备份数据库，执行 `python -m agenteval init-db` 升至 0007，重新构建并启动。固定 DDL 增加 IssueScope、QualityPolicy 和类型/合并指针。历史已确认、修复中、待复测、关闭及有确认事件的重新开放记录保留正式类型；其余 open 作为待确认异常。每条历史记录保守回填来源版本。

新增回归覆盖双 Agent 共享 Benchmark 的指标/问题/决策隔离，历史问题不阻断其他版本、显式扩展范围才阻断，跨 Benchmark/用例内容隔离，自动/手动模式、忽略幂等、批量合并/分配/冲突回滚、跨 Agent 复测拒绝，以及带历史数据的 0006→0007 迁移。公开 API 产品 smoke 在 SQLite 和 CI PostgreSQL 上验证范围与阻断快照。
