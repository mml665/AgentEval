# 0.11：产品流程补齐（批次 C）

日期：2026-11-05。对应 TEAM_RELEASE_OPTIMIZATION_SPEC 的 AE-104、105、109、110、111。本轮补齐这些开发流程，不新增评分器或 Agent 框架。真实业务、模型校准、用户效率和当前发布包全栈灾备仍按 AE-004 待验，不能据此标记团队正式上线。

## 2. 预检、复用与提交确认

“开始评测”保留三步新接入，新增已有版本入口。新 Agent 可填写版本名、选择目标、编辑测试用例及重复次数/并发/超时；已有路径只选择固定 AgentVersion、BenchmarkVersion、ProfileVersion，不重复注册资源。更改已有方案的执行策略需发布新 ProfileVersion，不能修改已冻结版本。

评测详情的“复制配置评测”只传资源引用和来源 Run ID，不从脱敏的历史 JSON 反推原始输入，也不覆盖来源运行。新提交生成新 Run。当前授权项目所有相关版本通过分页接口加载，不局限工作台的资源首页。

执行按钮需要先“预检并核对配置”。摘要展示三种固定版本、有效用例数、计划 Trial、重复次数、并发、超时、Judge 初始/含重试调用上限和持久化调用预算。调用上限受预算约束，不是金额估算。配置变化会清除旧预览并生成新请求键。

预览与正式执行共享 `preflight.check_material`，检查部署注册/HTTP 允许清单、凭据引用、观测能力、断言、核心用例、工具故障边界、副作用重试、状态环境和 Judge 配置/预算。新接入在任何资源写入前完成同一套检查，最终执行仍再次验证；预览不发送 Agent POST，不创建业务资源，但会有操作审计。

```http
POST /api/v1/onboarding/preview          # GuidedRun，新接入预览
POST /api/v1/onboarding/reuse-preview    # 以下 ReuseRun，已有版本预览
POST /api/v1/onboarding/reuse            # 同结构，实际创建新运行
GET  /api/v1/evaluations/{run_id}/reuse-config
GET  /api/v1/workspace-versions/{project_id}?offset=0&limit=100
```

```json
{"project_id":"<project>","request_key":"<random-UUID>","agent_version_id":"<AV>","benchmark_version_id":"<BV>","profile_version_id":"<PV>"}
```

复用使用原有 RequestDedup 和事务提交协议，相同键/请求返回原 Run；同键不同引用返回 409。三种引用及声明项目必须一致，服务端按实际外键授权。SDK 可直接调用 `client.post('onboarding/reuse-preview', body)`、`client.post('onboarding/reuse', body)`，机器令牌仍受项目和 evaluate 权限约束。

响应丢失或 5xx 时界面进入“提交结果尚未确认”，保留原请求键与配置。先通过 `GET /onboarding/requests/{request_key}?project_id=…` 查询已提交结果；发现原 Run 则直接打开。未发现不等于从未执行，可能仍在途；重试沿用同键，事务唯一约束阻止重复提交。只有显式返回修改并改变参数时才换键。个人模式在发送执行请求前保存带 pending_submission 的服务端草稿，刷新后恢复并查询，不自动重发。

## 3. 用例编辑、预检与版本差异

导入界面保留原始文档，高级 JSON/JSONL 与表格同步。单条编辑使用完整对象，保留嵌套 input/assertions/tags；缺少必需字段或存在未知字段时明确校验失败，不静默丢弃。可选同项目 AgentVersion/ProfileVersion 进行观测能力和断言兼容性检查。

```http
POST /api/v1/benchmarks/{benchmark_id}/preview
POST /api/v1/benchmarks/{benchmark_id}/publish
GET  /api/v1/benchmark-versions/{version_id}/diff?other_version_id=…
```

预览/发布接收 `document` 原文、`version`、可选 `agent_version_id`/`profile_version_id`。预览返回 parsed_case_count、valid_case_count、source_hash、错误及最多 100 条派生预览。错误带 row、对象起始 line、字段路径、case_key/评分项（可获取时）；JSON 语法错误另含 column。JSONL 空行不会导致行号偏移，格式化 JSON 和 cases 包装也按实际源文定位。有效用例范围 1–1000，非法 JSON、重复 case_key、缺少断言、非有限数或目标不兼容不能发布。

发布重新校验原始请求，事务内生成不可变版本和全部用例。预览失败无半套版本；相同版本名冲突不覆盖。旧 `/benchmarks/{id}/versions` API 保留原结构兼容，控制台导入改用新预检/发布路径。

预览响应经过展示脱敏，不能拿其内容覆盖原始文档；编辑器保留作者的原始输入，提交原文。版本差异只比较同一 Benchmark 身份，服务端在原文上计算 added/removed/modified/unchanged，再对 before/after 视图脱敏。差异查看不提供修改旧版本的通道。CSV/Excel 和任意字段映射不在本轮。

## 4. 显式基线、批次与 URL

```http
GET/POST /api/v1/quality/baselines/{project_id}
```

保存字段为 `agent_id`、`benchmark_version_id`、`grading_batch_id`、`expected_revision`（首次 0）。必须是同项目、同 Agent、同 Benchmark 固定版本的已完成评分批次及已稳定运行；项目评测成员可保存，只读成员不能写。修订冲突返回 409，保存实际 actor 和请求审计关联。

基线按固定 BV 划分，未配置时提示选择，不把最新/最旧运行当作“已发布基线”。默认候选可以是当前已完成运行，但基线只来自已保存设置或用户显式选择。交换只改变比较方向，保存才更新默认基线。晚到的旧版本运行或旧运行重评均不替换已保存批次。

范围链接携带 project_id、Agent/候选/基线/BV 和 candidate_batch_id/baseline_batch_id。服务端比较、工作台和发布记录均核对这些引用；同版本不同运行/批次不再混用指标。开放问题依旧按 IssueScope 的版本/用例适用性匹配，历史适用阻断项不会因换批次自动消失。

刷新、历史前后退和个人会话恢复/重新登录恢复有效链接；无权限、失效版本或错误批次明确提示，不静默切换到其他项目/Agent。切项目时重新创建范围上下文，旧请求不能回写新项目 URL。详情跳转比较/发布会沿用实际固定证据上下文。

## 5. 发布快照与当前有效性

后端 status 保留 ready/blocked/insufficient；ready 文案为“当前评测范围满足门禁”，不表示已部署或生产审批完成。新发布快照追加生成时门禁阈值、Benchmark 身份/版本/用例数及样本数。历史缺失元数据明确提示未记录，不用当前规则回填历史结论。

读取详情、列表、工作台及导出另返回 `current_validity`：current、reason codes、checked_at。两侧出现更新评分批次、引擎需重评或候选范围的开放阻断项集合/修订变化时，提示重新比较和评估。其他 Agent 的问题不影响该候选。即使历史阻断项已修复，旧 blocked 仍保留，需要新评估。

此信息在 snapshot 外派生，旧 status、snapshot 和引用不改写。页面每 10 秒及窗口重新聚焦更新详情，并有手动刷新；失效报告使用“历史评估”提示。JSON/HTML 导出包含检查时间，与生成时证据明确区分；导出内容哈希是本次派生文件的摘要，不是改写原始证据哈希。

## 6. 服务端个人草稿与敏感数据边界

```http
GET/POST /api/v1/onboarding/drafts/{project_id}
```

仅个人账户使用，按 user_id + project_id 唯一；POST 使用 expected_revision 和严格 DraftState payload，保存 UI 配置、阶段、原请求键、用例原文及版本引用。角色/项目、嵌套资源和凭据引用仍需授权；endpoint 禁止内嵌鉴权和 query/fragment。Cookie 写入继续要求 Origin/CSRF，机器和 legacy 身份均不能存取私人草稿。

默认不自动覆盖已有草稿，用户可手动保存和选择恢复。恢复读取**本人先前提交的输入**，经授权返回原文并标记 `X-AgentEval-View: private-owner-draft`，这是编辑用途的专门设计例外；不能借此读取服务器原始评测证据或其他成员草稿，部署管理员也不能通过此接口枚举他人草稿。输入不进入 localStorage/sessionStorage，退出/换用户卸载内存。原始证据读取仍走 0.10 的个人专项权限和理由审计入口。

草稿含可能敏感的作者输入，数据库/整库备份须受部署访问控制；项目归档排除 evaluation_drafts，恢复项目不导入个人草稿。当前保存一份最新草稿，使用修订防止其他标签页覆盖；不提供历史草稿或自动清理。未保存的内存输入无法保证在进程崩溃、强制结束或强制会话失效后恢复，因此需主动保存；正式提交前个人模式会保存用于响应丢失恢复的配置。

普通导航、切项目、退出和刷新有未保存提示；取消后保留当前页面与输入。网络失败保留输入，草稿保存失败不会误标为执行已提交，也不继续创建运行。

## 7. 迁移、归档与验收边界

停止旧 API/Worker/Dispatcher，确认无在途调用并备份数据库和发布包，执行 init-db 至 **0010**，前后端同步升级至 0.11。新增 baseline_settings/evaluation_drafts，不改写历史任务、评分或快照。**历史项目不自动回填基线**，需确认固定批次后保存。已有会话和角色模型继续生效；无需添加模型密钥，个人账户初始化仍按 0.9 说明。

项目归档升级为 project-archive-v2 / database_revision 0010，保留显式基线，排除个人草稿及授权。旧 v1/0009 签名包仍可验证，恢复目标须先升级到 0010，缺少的基线表按空集恢复；原文件不改写。旧程序不能理解新 v2 包，不应把新包作为旧版本回退依据。恢复仍限隔离空业务库，不覆盖现有预览或生产库。

本轮增加后端产品合同与旧归档兼容回归，浏览器补充复制配置、取消离开、服务端草稿刷新恢复、真实提交后模拟丢失响应、原请求查询、晚到运行/显式基线、批次 URL/登录/历史/交换方向和复杂用例编辑/差异。CI 的 PostgreSQL team_smoke 增加复制幂等、私人草稿、显式基线、用例发布/差异及发布时效；项目恢复 smoke 包含新基线数据。

准确测试数量与提交 CI 见 README/BUILD_STATUS；截图 workflow-*.png 为明确夹具。P1 流程开发补齐不等于全部产品验收完成：AE-001 真实鉴权业务、AE-003 项目敏感规则/容量/存储权限、AE-004 两真实 Agent/实际 Judge/用户试用/当前 Compose 灾备仍待资源。AE-201 有关键页面尺寸和交互证据，不代表所有页面均经完整无障碍认证。

CI 分页回归曾在手动刷新尚未完成时采集旧列表，记录数同为 10 不能证明数据已经刷新。现资源页在加载中禁用翻页并标记 aria-busy，测试通过可控延迟核验禁用状态，再等待最新新增记录可见后比较前后页，保留不重叠断言。该修复不增加测试数量，也不使用固定延时或自动重跑掩盖失败。
